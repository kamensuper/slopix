# Slopix 0.9 Light — first-run setup and sign-in experiment

This is a **real source-code integration** into Slopix's existing C desktop service, not a mockup or an external Linux installer.
It is an experimental feature based on the original uploaded 0.9 Light baseline; it is not a verified bootable release.

## User experience

1. First start (when `ACCOUNT.DAT` does not exist): a full-screen Slopix Welcome assistant.
2. Ask for a name (1–24 characters: ASCII letters, digits, spaces, underscore, period, hyphen).
3. Ask for a password (6–63 characters), then ask to confirm it.
4. Save `ACCOUNT.DAT` to the mounted FAT32 data disk, with a per-account salt and PBKDF2-HMAC-SHA256 password verifier (12,000 iterations). **Plaintext passwords are not written to disk.**
5. Show the dark, teal-gradient Slopix login screen, avatar and masked password entry, plus a big clock where screen height permits it.
6. Only after a correct password does SlopDE receive normal rendering and keyboard/mouse input.
7. On subsequent boots, skip setup, load the account from the data disk, and show the login screen.

Press **Enter** to continue and **Escape** to go back during setup. The Next/Unlock button can also be clicked. If no writable FAT32 disk is mounted, a **session-only** account is created and setup will repeat on every restart. If an `ACCOUNT.DAT` file is found but malformed, boot stops at a recovery notice rather than silently overwriting it.

## Fedora build

From the extracted `slopix-0.9-light` project folder:

```bash
make -j4
ls -lh build/slopix.iso
make run
```

The default Makefile target builds the ISO; **there is no `make iso` target**. The build directory is omitted from this archive intentionally, so the shipped ZIP cannot accidentally launch an OLD 0.9 ISO without the new setup. The ISO must be rebuilt before booting. Slopix needs GCC, GNU binutils, Rust for `x86_64-unknown-none`, GRUB BIOS ISO utilities, xorriso, Python 3, and QEMU. If the Rust target is missing from a rustup installation, use `rustup target add x86_64-unknown-none`.

The ZIP includes a copy of the original release's FAT32 data image. For an independent experiment, create a backup of `storage/slopix-data.img` first and never replace an image containing user files. To create a **new** disk, run `python3 tools/create_disk.py path/to/a/new.img` and put it in place of the test disk (only after copying the old one elsewhere).

## Tests run by the authoring environment

- `make account-test`: **PASS**, including independent PBKDF2-SHA256 reference vector, storage readback, incorrect password, corrupted file, write failure, and no-disk session mode.
- `make auth-flow-test`: **PASS**, covering first-boot wizard, wrong and correct password, later boot requiring login, and corrupt-record guard.
- `make boundaries-test`: **PASS**, desktop backend routing, using its authorized test double.
- New kernel C files and the modified desktop-service C file compiled with GCC `-Werror` and freestanding x86-64 flags.
- **NOT VERIFIED:** full Rust+GRUB ISO build, QEMU boot, FAT32 persistence in a real guest across power cycles, graphical input/render output. Those tools are not installed and could not be obtained in the authoring environment.
- Many existing QEMU regression scripts assume the desktop opens immediately; those scripts need updated login/setup automation before `make test` can be considered a full pass.

## Limitations / security

This is a **single-account graphical login gate**, not a hardened security model. Slopix 0.9 still has kernel-integrated GUI applications; there are no disk-access controls or encrypted volumes. Password salts use timer and input-event entropy and **are not generated by a verified CSPRNG**; the iteration count is modest by current security standards. FAT32 is unencrypted; physical disk access or a modified kernel bypasses the screen. A person who forgets the password must repair or replace the account record on the data image after backing it up. It is not intended to protect sensitive data.

No Cube/DOOM Ring-3 migration or lifecycle rewrite is included in this change. Earlier reported close/reopen bugs remain separate issues.
